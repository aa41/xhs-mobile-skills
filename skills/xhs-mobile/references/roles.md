# 角色设定

所有角色都服务于同一个目标：**把进展讲成用户能感知到的「App/网页有了什么变化」**，而不是技术叙事。

## daily-dev-log / 每日开发日志

适用：一天内的进展、修 bug、排查问题、小范围改动。

声音：
- 像当天随手记下的复盘。
- 允许出现小挫折、取舍、具体时间点。
- 少讲宏大价值，多讲今天实际改了什么、用户那边会感觉到什么。

标题方向：
- `今天把发布卡顿的问题收了个尾`
- `一个闪退，最后查到是缓存没清`
- `分享链路里最容易漏掉的 3 个状态`

## weekly-dev-log / 每周开发日志

适用：一周总结、多项进展、阶段性复盘。

声音：
- 有节奏地归纳，不写流水账。
- 每一节有具体证据：功能、指标、截图、失败案例、遗留问题。
- 保留一两个没做完的点，显得真实。

## release-note / 版本更新

适用：版本发布、新功能、修复、迁移说明。

声音：
- 清楚、克制、可执行。
- 用户先看到「这次有什么用」，再看细节。
- 不写「重磅」「全面升级」「焕新上线」等空词。

结构：
1. 一句话说明版本变化（用户视角）。
2. 新增 / 修复 / 调整（只挑用户能感知的）。
3. 影响用户的注意事项。
4. 幕后或下一步。

## daily-ops / 日常运营

适用：运营动作、内容策略、数据复盘、投放/活动小结。

声音：
- 像运营同学在复盘为什么这么做。
- 讲动作与反馈，不只讲结论。
- 数据能具体就具体，不能具体就讲观察口径。

标题方向：
- `这条笔记没爆，但评论区给了一个新选题`
- `今天把标签从 9 个收到了 5 个`
- `一次小活动复盘：有效的是提醒，不是海报`

## product-diary / 产品日记

适用：产品决策、用户反馈、体验优化、路线取舍。

声音：
- 以用户场景和取舍为中心。
- 可以写「为什么不做某个功能」。
- 保持温和，不替用户下结论。

## 通用禁用词

避免或删除：`在这个快节奏的时代`、`赋能`、`全面升级`、`重磅上线`、`焕新`、`以下是`、`希望对你有帮助`、`让我们一起`、`不难发现`、`作为一个 AI`。
