# 文案与视觉风格

## 核心原则：面向用户，不要技术叙事

读者是普通用户，不是工程师。判断一条信息要不要写，只问一句：**用户用 App/网页时会不会感觉到？**

- ✅ 要写：「分享到小红书时图片更清晰了」「长按可以复制链接了」「加载慢的页面现在快了一截」。
- ❌ 不写：「升级了 OkHttp 到 5.x」「把 Retrofit 换成 Ktor」「重构了网络层」「CI 改用 GitHub Actions」。
- 技术升级若带来用户可感知的变化，**只写变化本身**，不写实现。例：依赖升级让启动变快 → 写「打开 App 快了」，不写「升级了 xxx 库」。

## 反 AI 味

AI 味通常来自四类问题：

1. **空泛**：只有「优化体验」「提升效率」，没有具体对象。
2. **翻译味**：句式像英文转中文，例如「我们很兴奋地宣布」。
3. **过度完整**：每段都整齐总结，像报告模板。
4. **结尾套话**：感谢阅读、希望有帮助、一起进步。

修法：
- 用当天发生的具体事替代抽象判断。
- 每 80–120 字给一个实物：功能名、截图、错误码、用户反馈、耗时。
- 保留合理的不完美：绕路、失败、未完成、下一步。
- 中文句子短一点，少用「因此 / 首先 / 其次 / 最后」。

## 小红书文案

- 标题 16–28 个中文字，包含具体对象。
- 开头第一句不要铺垫，直接给场景或冲突。
- 标签 3–8 个，不要堆无关热词。
- 正文短段落，每段只说一个点。

## 小红书图片

竖版 `1024x1536`，适合手机首屏。常见卡片：封面 / 问题卡 / 过程卡 / 结果卡 / 总结卡。
视觉关键词见 [card-design.md](card-design.md)——必须同时指定 **Style × Layout × Palette**。

## 微信公众号文章

- 标题比小红书更耐读，少用夸张语气。
- 摘要不超过 120 字，直接说明文章价值。
- 正文可以更完整，但段落要短。
- 公众号发布边界见 [sharing.md](sharing.md)：第三方 App 无可靠 scheme 直达草稿，走「复制正文 + 打开编辑器」。
